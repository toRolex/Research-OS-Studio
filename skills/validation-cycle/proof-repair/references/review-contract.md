# proof-review 交接与独立复审

`proof-review` 是唯一审查入口，须实际为可被 model 调用的技能。运行时先确认它存在且调用机制允许；不存在、仅 user-invoked、未获得原文外发授权或无法提供所需隔离时，停止并报告缺项。这里不假定任何 provider、模型、工具参数或“跨模型已保证”；不得编造调用回执，也不安装或切换审查后端。

## 送审材料

首次审查和每轮复审均提供：本次范围、完整目标命题及假设/定义、实际当前完整证明原文、所有相关附录和上游引用所用定理的完整适用内容、下游应用原文、六份义务账本及适用检查清单。每份原文有路径与段落/标签定位，直接提供正文或经确认可完整读取的资源；不能只传路径后假定已读。全文过大时将完整内容按可核对边界分批传递，在收齐并确认覆盖前不请求全局结论；无法完整传递即停止，不换成摘要。

常规复审可引用同一次运行中审查者自己的完整前轮反馈，仅追踪问题是否解除，不添加执行器对旧批评的解释或诱导性裁定。实际修后推导、新义务、assumption delta 和用户决定作为可核对的原始材料提供；BEFORE/AFTER 历史保留在 repair 记录，不用修复者的优点陈述、改动摘要或推荐结论引导审查。审查者先独立读取当前完整原文再逐项追踪。新一次用户调用从新的审查上下文开始，不拿旧通过结论代替当前原文审查。

## 每次完整审查

要求 `proof-review` 完整执行它自带的六类义务、A–H、分类、侧条件、反例与全局闭合规则，对每个结果及每次应用给出依据或缺口；它的规则及问题字段以该 Skill 为唯一权威位置。修复记录保留返回的每条自然 Markdown 发现全文，不压缩为“通过”或省略未解问题。

`proof-review` 只返回回复，所有文件零写入、不编译；落盘反馈由 repair 在自身获准路径处理。独立安装 repair 而 proof-review 缺失时，明确记录“独立复审未完成，请用户补齐 proof-review”，不以自检顶替通过。

`--deep-fix` 只追加执行器按深修复模板写出的完整计划供审查，不要求 proof-review 生成补丁，不能替代 A–H 或问题字段。计划不可用而常规审查有效时保留常规反馈；整个审查失败则停。超时、传输失败等可能已执行的调用不盲目重发；先说明不确定性，请用户决定。

## FATAL/CRITICAL 修复的 fresh 盲审

凡试图解除 FATAL 或 CRITICAL 的修复，在常规复审后另调用 proof-review 的真实新上下文。该上下文只收到修后完整章节原文以及理解/验证所必需的完整定义、假设、上游和下游原文；不收到旧批评、问题编号、严重度、修复日志、差异、先前结论或带提示的修复摘要。

盲审任务文本：

> 对以下完整证明原文进行独立审查。逐步检查正确性、隐藏假设、非法交换与反例，执行 A–H 清单并记录所有缺口。你没有先前审查或讨论的上下文。材料如下。

只有实际具备新上下文隔离时才声称“盲审”。不能以在同一会话内要求忘记旧批评冒充 fresh；没有该能力就停止重大修复验收。盲审反馈完整保留，任何新问题进入下一轮，不在当前轮无上限补丁。盲审局部通过仍须全局闭合，不能替代 DAG、下游与 assumption delta 检查。

## 审查回传与诚实结论

保留反馈完整原文并逐项对照原证明、实际补丁和新义务；有异议写出数学理由再送 proof-review，不把执行器赞同或反对当成审查已关闭。审查者缺少材料、回复截断或只给总体赞同，没有逐项义务依据时说明不足并停止验收。

检查回传的实际审查角色及独立性。调用名为 proof-review 不自动证明独立；作者本人执行的“非独立自查”可辅助修复并完整保留，但必须记录“独立复核未完成”，不得据此宣布修复通过，等待用户补齐获准的独立审查。fresh 还须额外满足前述上下文隔离。

最终区分“全部义务闭合”“仅表述问题仍开放”“存在数学缺口”“以未验证导入为前提”“来源/审查不可用”“不适用”；每种结论写出实际证据和边界，不生成统一 verdict JSON、状态文件或额外验收程序。
