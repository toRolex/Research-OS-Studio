# Maintain Formal Verification Skill：维护形式化检查

形式检查证明的是它所描述对象的一条性质。代码变了而验证没变时，检查可能继续通过，却在描述已经不存在的代码。这种通过最危险，因为它看起来像证明。本 Skill 是维护闭环：用于 `create-formal-verification-skill` 生成的项目本地 verify skill，或任何对具名代码运行模型检查器、证明助手或代码级验证器的项目本地 skill。

项目本地 skill 处理执行者使用它时自己造成的改动；本 Skill 处理跳过它的变化：合并、未用该 skill 的编辑，以及跨多个提交累积的漂移。

Gates: none

## 委托继承

一次调用继承本次研究委托的目标、权限与额度；写验证资产与项目内依赖准备在授权内进行，越权、超额、未授权的全局安装、外部上传或产品代码修复仍需用户决定。用户只要诊断、只读审查或只判断漂移时，保持该范围，不改验证也不改代码。需要独立复算或并行核对时以当前会话确实可调用的子代理工具为前提；没有时该步标 blocked 并写明缺口，不由编排者串行代跑冒充独立复核。普通证明的审查与修复属于 proof 族能力，本 Skill 不替代。

## 结果分类

每条检查给一个结果，并说明是哪一个：

- **in sync**：自上次同步以来没有改动改变检查所描述的对象，且检查通过。
- **updated**：代码变了，验证已改为描述新代码，且检查通过。
- **bug**：验证描述的是当前代码，而代码违反该性质。这是关于代码的发现，不是漂移。
- **blocked**：检查无法重新对齐或无法运行。写明具体原因。

一条检查可以同时是 updated 与 bug：更新使验证重新描述代码，随后该性质在新代码上失败。

相关对象变化先标为 **stale**（待重新对齐）；不能因为 HEAD 未变或旧模型仍通过而沿用旧结论。

## 权限边界

只改验证：模型、harness、性质文件、假设账本、对应审计记录与 verify skill 本身。运行期间不改产品代码，除非用户要求。当前代码上性质失败时，不削弱性质或模型来制造通过，报告失败。

外部假设、材料或依赖版本变化时，先更新记录再判断结果；旧通过不自动替新对象背书。需要升级工具、拉取外部材料或做其他外部动作时按委托权限处理，缺授权只阻塞那一步。

## 维护流程

1. **找到检查。** verify skill 没有固定名字，按行为找：对具名代码运行模型检查器、证明助手或其他验证器的项目 skill。读取找到的每一个，或用户点名的那个。对每条检查收集：性质、覆盖代码、界与假设、外部假设与依赖版本、运行命令，以及最后一次确认它描述当前代码的同步对象记录。记录包括 commit 和实际输入清单：覆盖代码、模型、harness、性质及配置的路径与内容摘要（如 SHA256），并标出工作树差异与相关未跟踪文件。没有 verify skill 时停止并指向 `create-formal-verification-skill`。旧记录只有 commit 或根本无同步记录时，提交历史只作定位线索，不推定工作树干净或曾验证当前对象；先标未核实，重新建立输入记录和证据。

2. **按原样运行。** 保存本次实际输入清单，再在改动任何东西前各跑一次并记录结果。检查工具或必要输入缺失时标 blocked，不用旧通过补位。这里的通过不代表代码正确，只说明旧描述仍然成立。这里的失败可能是漂移也可能是 bug，未到第 5 步不要下结论。

3. **读遍覆盖代码的改动。** 比较上次同步对象与本次实际输入，而不只比较两个 commit：读同步 commit 到 HEAD 的 diff/提交信息、已暂存与未暂存 diff，并检查相关未跟踪文件的内容。可用 `git diff <同步commit> HEAD`、`git diff --cached`、`git diff`、`git ls-files --others --exclude-standard` 定位；实际读取的相关输入即使被忽略也须纳入清单。与保存的路径/摘要对账，包含新增、删除及验证输入资产的变化；HEAD 相同也不跳过。相关变化先使旧结果 stale。同时找移动过的代码：被改名、拆分、搬到别的文件的覆盖函数仍属覆盖代码。再找触及被守护状态的新代码，例如写入同一字段的新函数。对每处改动判定：
   - **无影响**：格式化、注释、验证不覆盖的代码路径等不改变检查描述的对象。按模型或 harness 判断，不按提交信息判断。
   - **验证不再描述代码**：原本不可分的一步变成两步，分支增删，检查位置移动，新路径抵达被守护状态，或取值范围改变。模型或 harness 必须改。
   - **承诺被有意改变**：改动改变了代码承诺，且改动中有证据表明这是有意的：文档注释、测试、变更日志或提交信息。性质必须改，并引用该证据。
   - **承诺可能被破坏**：代码变了，且没有证据表明承诺改变。随之而来的失败按 bug 候选处理。

4. **按代码更新，不按结果更新。** 修改模型或 harness，使每个变化部分重新指向审查者可打开的代码，代码里不可分的一步在验证里仍是不可分的一步。先按代码写完更新再重跑，不按「怎样能通过」塑形。只在承诺被有意改变时修改性质，并写下旧表述、新表述与证据。除改动使界错误外保持原界；必须降低界时在报告中说明。

5. **同步外部假设、版本与对应审计。** 更新假设账本中的工具与标准库版本、外部材料与定义版本、覆盖范围与重验触发。原问题、编码定义或定理声明有变化时重做对应审计：对象、量词、假设、定义域与结论强度是否仍一致。占位符、编译成功或有限数值结果不得升级为原定理成立；被改动削弱或换题的检查按未完成处理。任何一个假设或版本变化都使旧通过失效，标为 stale 而不是沿用。

6. **重跑并判断每个结果。**
   - **通过**：通过也可能来自一个已经失去失败能力的描述。按性质守护的方式破坏新代码（去掉新检查、调换新步骤），确认检查能抓住，然后撤销破坏。
   - **失败**：把反例逐步对回真实代码。某一步在代码中不可能发生时，是验证写错了：修验证并说明哪里错。每一步都可能发生时，是 bug：指出引入它的 commit；尚未提交时给出工作树差异与位置，不编造 commit。用代码自己的话把反例讲成步骤序列，用一句话说明危害。若针对真实代码的廉价测试或复现能证明该 bug，把它作为证据写进报告，不提交到产品代码。

7. **更新 verify skill。** 重跑及撤销故障变体后，复核输入与本次实际核对、运行的对象一致；运行期间若有未审变化，结果仍 stale，重新对齐并重跑，不能移动同步记录。证据齐备后更新每条检查的覆盖代码、命令、界、假设与版本、对应审计及同步对象记录（commit、实际路径/摘要、工作树差异、日期和命令/结果）。有未提交输入时如实记录，不能用 HEAD 代替；blocked 的检查保留旧同步记录并报告本次缺口。然后把 verify skill 当作下一个执行者走一遍，确认步骤仍可运行。

## 报告

对每条检查报告：

- 结果、读过的 commit 及实际输入清单/摘要、已暂存/未暂存/相关未跟踪变化；
- 验证里改了什么、为什么，每处给简短理由：代码改变形状，或承诺被有意改变（附证据）；
- 重跑结果，以及用来证明更新后的检查仍能失败的那次破坏；
- 每个 bug 的平实描述：用代码语言讲的反例步骤、危害、引入它的 commit 或未提交差异位置；
- 验证仍不覆盖什么，包括本应覆盖而未覆盖的新代码；
- 外部假设、材料与依赖版本的实际变化，以及哪条旧结果因此失效。

明确说出哪些失败是验证漂移、哪些是代码 bug。对更新前通过、更新后失败的检查，说明旧通过建立在过期描述上。

验证的更新单独成一份改动，与任何产品修复分开。宿主中立：不写死个人目录、固定模型或厂商专属命令；缺子代理时独立复算标 blocked；静态检查与一次安装成功只证明结构与可达性，不证明数学结论成立。
