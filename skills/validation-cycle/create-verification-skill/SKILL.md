# Create Verification Skill：建立项目行为验证 Skill

每个认真维护的项目都需要一种可脚本化的方式驱动真实应用并证明行为：启动它，按用户会用的方式行使某个功能，并留下可检查的证据。本 Skill 调查仓库后生成一个项目本地 verify skill，写给下一个从没见过这个应用的执行者冷读，不写给人预览。

本 Skill 处理软件行为验证：启动、驱动、观察运行中的程序。它不宣称数学定理成立，也不冒充形式化检查；需要对代码性质、形式模型或定理编码做范围内每种情况的检查时，使用 `create-formal-verification-skill`。

Gates: none

## 委托继承

一次调用继承本次研究委托的目标、权限与额度：项目内依赖准备与启动应用属于授权内的项目内动作，写验证资产是项目内准备；越权、超额、未授权的全局安装或外部上传仍需用户决定。用户只要调查、只读审查或只写生成计划时，保持该范围，不启动应用也不落盘资产。需要并行调查或独立复核时以当前会话确实可调用的子代理工具为前提；没有时该步标 blocked 并写明缺口，不由编排者串行代跑冒充独立复核。

## 1. 采访仓库，不是用户

答案从代码库来，只问观察不到的事：

- **表面（Surface）**：用户实际触碰什么？Web UI、CLI/TUI、桌面应用、API、移动端还是库？一个仓库可以有多个；选定主表面并记录其余。
- **启动（Launch）**：应用本地怎么跑起来？优先用仓库自己文档化的 dev 命令（package scripts、Makefile、README quickstart）。记录端口、环境变量、种子数据、认证。启动必须从空数据目录达到可用状态，包括迁移与种子数据；「可用」不是「进程有响应」——数据库健康检查通过时初始化脚本可能仍在跑。包含拆卸。
- **驱动（Drive）**：执行者如何程序化交互？先用已有 harness——Playwright/Cypress 规格、expect 脚本、PTY 助手、可 curl 的端点、debug 端口；再考虑通用配方：Web/Electron 用 browser/CDP，CLI/TUI 用 tmux/PTY harness，服务用 HTTP。优先稳定句柄（ARIA 标签、data 属性、提示串、路由路径），不用坐标和 tab 顺序。
- **观察（Evidence）**：能采到什么证据？截图、终端转录、响应体、日志、退出码、数据库状态。
- **隔离（Isolate）**：两个实例能否并存（端口、数据目录、profile）？不能时在生成的 skill 里写明：拒绝对共享实例二次驱动，好过弄坏用户的会话。

短命 CLI/TUI 没有常驻服务：启动意味着构建一次二进制（或装依赖），每次驱动在自己的隔离 PTY 或 tmux 会话里进行。

checkout 本身构建或启动失败时，先修好（或精确报告）再生成；对启动无关的缺失资产（API 从不 serve 的静态目录、示例配置），生成的 skill 可以创建它，明确标为验证脚手架，并在清理中移除。执行失败或项目不可达时如实说明，清理后保留证据，不伪造成已验证。

## 2. 生成 skill

写项目本地 `verify-<app>/SKILL.md`，frontmatter 含 `name: verify-<app>` 和说明应用、表面与何时使用的 `description`；没有 frontmatter 的说明不会注册。各小节必须落在调查的真实发现上，不留占位符：

- **启动**：启动应用的确切命令，以及如何判断就绪（一条日志行、一个提示符），含拆卸。
- **Doctor**：一条只读检查回答「这个实例值得驱动吗」——进程在、版本/构建对、端口归我们、认证有效。任何异常时执行者先跑这条。
- **驱动**：用本仓库真实选择器/命令的 harness 配方，不是示例。
- **证据**：采什么、放哪里，并写明证明标准：行使真实用户路径，不是内部 setter 或 test-only 端点；同时采集动作与结果状态，不只截最终画面；旁证副作用（文件、数据库行、发出的消息）；mock 只用于生产边界已隔离的外部系统。安全路径是 dry-run 或 test mode 时，用观察（文件、网络、git refs）核实它到底跳过了什么，不轻信名字。
  - **证据归属与失效**：生成的 Skill 必须要求每轮证据绑定实际被测对象：记录代码 revision、工作区脏改动差异（或明确无改动）、关键输入/数据与依赖和工具链版本、验证资产版本，以及适用范围与假设。相关代码、输入、依赖、工具链或验证资产变化时，立即把受影响结果标为 `stale`/待验证；保留旧证据作历史，但不得为新对象背书。只有重跑受影响覆盖并记录新的对象绑定，结果才能恢复为已验证；无关结果不必作废。
- **清理**：拆掉本次运行创建的实例。不按进程名杀；只杀自己启动的。清理移除实例与草稿状态，从不移除证据：证明产物在拆卸后仍留在 skill 命名的位置。
- **Helpers**：skill 附带的每个脚本可执行，且调用方式写在正文里；要读者逆向工程的脚本不是 helper。

## 3. 播种特征覆盖映射

创建 `verify-<app>/features/README.md` 加每个用户可见特征一个文件（从路由、命令、菜单或文档里挑，先 3-5 个）。形状见[特征映射示例](references/feature-map-example/README.md)：索引加每特征一文件，回答用户视角的四个问题——特征是什么、怎么到达、怎么用 harness 驱动、什么可观察终态证明它工作。小节固定为 `Sub-features`、`How to get to it (user POV)`、`Driving it with <harness>` 和 `Gotchas`。种子数据缺某旅程需要的前置条件时，该旅程如实报告失败并把原因写进 `Gotchas`；不削弱旅程来换通过。

覆盖映射是仓库持续维护的验证来源：只驱动一个顺手的入口不算完整证明，映射列出的其他特征仍在覆盖要求之内。特征索引与文件的一致性可用随附 helper `helpers/feature-map-lint.py` 检查（用法见该文件头部说明）。

## 4. 交付前自证，未执行即草稿

按生成的 skill 自己的说明端到端跑一遍：启动、doctor、驱动一个已映射特征（一个就够；映射存在的意义是让后续运行覆盖其余）、采证据、清理。清理后确认证据仍在命名位置——吃掉证明的清理不通过。失败就修，每次失败的迭代也跑生成的清理，不让坏尝试留下进程和端口。

从未执行过的生成 skill 只能标为草稿，不是交付物；草稿状态写进 skill 本身，不宣称可用。在替身（容器代真机、本地栈代远程）上证明过时，逐项列出替身做了而真实目标不会有的步骤；这些步骤在真实目标上跑过之前保持未验证。自证记录也须遵守「证据归属与失效」合同。

## 5. 交接与维护闭环

交付时告诉用户：验证了什么、怎么运行、覆盖映射包含什么、还有什么没验证（草稿、替身差距、不可达前置条件）。需要随应用变化保持映射诚实时，指向 `maintain-verification-skill`；维护轮次用真实启动、doctor、驱动与证据补全映射的其余覆盖。只在用户问及时建议节奏。

宿主中立：不写死任何宿主品牌、个人目录、固定模型或厂商专属命令；harness 按项目实际栈选择。静态结构检查与安装成功只证明合同与可达性，不证明应用行为已被验证。
