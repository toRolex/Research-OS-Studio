# 工具选择：让问题决定工具

先写清要回答的问题和它的对象类别，再选工具。工具名可以随项目变化，判据不随之变化。

## 四类对象

| 类别 | 典型问题 | 首选工具类别 | 足够 | 不够 |
|---|---|---|---|---|
| 代码性质 | 「这段实现对每个输入都满足该不变量吗」；越界、溢出、别名、unsafe 访问 | 跑在真实代码上的验证器、SMT 支撑检查器、带断言的契约检查 | 工具能覆盖的语言与边界，且能对坏变体失败 | 语言无验证器；跨模块调用未建模；只测了采样输入 |
| 形式模型 | 「事件能以坏顺序发生吗」；并发、重试、状态机、协议、解析器设计 | 小模型的模型检查 | 状态空间可穷举或有界，且模型步骤与代码步骤一一对应 | 模型比代码多一层抽象却无人核对；状态爆炸后被截断的界被当作全称结论 |
| 数学定理 | 「对每个规模都成立，界不够」；一般性命题、精确证明义务 | 证明助手、精确证明义务链 | 编码声明与原问题逐项对应，无占位符与未声明公理 | 只有编译通过；有占位符、未定义假设或被吞掉的公理；界内结果被当成一般定理 |
| 普通测试 | 「这个输入、这个回归、这个边界是否正确」 | 单元测试、生成输入测试、属性测试 | 覆盖声明的输入域，失败可复现 | 被当作全称证明；未声明的输入域被默认覆盖 |

## 判据

1. **先问范围**：结论要覆盖「每一个输入 / 每一种交错 / 每一个规模」，还是「这些具体用例」。具体用例用普通测试，不升级成形式化门。
2. **再问对象**：要检查的是实现本身，还是设计层面的顺序与状态。实现用代码级工具，顺序与状态用模型检查。
3. **再问成本**：能在项目内安装、锁定版本、一条命令重跑的工具优先；需要长期维护的形式化只在收益明确时引入。
4. **最后问失败能力**：所选工具必须能在一个故意破坏的变体上失败。做不到时换工具或缩小声明范围。

## 不强制全链

- 不要求每条主张都造程序、每个反例都代码化、每项研究都全链形式化。
- 同一项目可以只对一条性质做形式化，其余用测试、审查或数值实验，并在记录中写明各自覆盖。
- 该语言没有可用验证器时，说明这一点，用生成输入测试真实代码，不用手写模型冒充代码。
- 缺少适用工具时如实说明并降级到最近的可核查手段；降级后的结果按实际手段命名，不借用形式化结论。

## 工具与版本记录

选定工具后，把下列内容写入假设账本：工具名与用途、版本或提交、安装方式、运行命令、输入与输出位置、已知限制。版本无法确定时留空并标未核实，不填猜测值。
