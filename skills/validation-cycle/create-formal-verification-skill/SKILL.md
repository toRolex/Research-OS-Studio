# Create Formal Verification Skill：建立形式化检查资产

测试只检查有人想到要写的用例；形式化在声明范围内检查每一种情况：模型里的每一种步骤顺序、某个界内的每一个输入，或每一个输入。本 Skill 找出项目里最值得这样检查的部分，验证它的一条性质，并留下一个项目本地 verify skill，让下一个执行者在改动时能对照该性质复查。

形式化是默认评估、按需尝试的能力，不是所有研究的全链门。四类对象必须先分清：代码性质、形式模型、数学定理、普通测试。只有当问题确实需要「范围内每一种情况」时才形式化；普通测试够用时说明理由并停止，不为了齐全而堆工具链。

Gates: none

## 委托继承

一次调用继承本次研究委托的目标、权限与额度：项目内依赖与检查工具可在授权内准备，写项目验证资产属于项目内准备；越权、超额、未授权的全局安装或外部上传仍需用户决定。用户只要评估、只读审查或只做对应审计时，保持该范围，不生成资产、不改产品代码。需要独立复核或 fan-out 时以当前会话确实可调用的子代理工具为前提；没有时该步标 blocked 并写明缺口，不由编排者串行代跑冒充独立复核。普通数学证明的生成、审查与修复属于 proof 族能力，本 Skill 不替代也不改写它们。

## 1. 从代码和问题选目标

答案从实际代码与用户材料里来，只问观察不到的事。用户点名了区域或 bug 时从那里开始。

好目标是代码作出的一个承诺：破坏它会伤到用户，而测试很少触达破坏它的那个情形。选仓库里最强的这类目标，不选最容易验证的那个。

先判定对象属于哪一类，并写明理由：

| 类别 | 问题形态 | 是否该形式化 |
|---|---|---|
| 代码性质 | 「这份实现对其语言的每个输入都满足某不变量吗」（内存安全、溢出、数据结构不变量） | 代码级验证器能跑在该语言上时，优先验证真实代码 |
| 形式模型 | 「这些事件能以坏顺序发生吗」「重试/状态机/协议在所有交错下安全吗」 | 对设计的小模型做模型检查，通常比验证全部代码便宜 |
| 数学定理 | 「该命题对每个规模都成立，界不够」 | 需要证明助手或精确证明义务；编码声明必须与原问题逐项对应 |
| 普通测试 | 「这个具体输入、回归、边界用例是否正确」 | 够用就停；形式化不替代普通测试，也不被要求为每个主张造程序 |

判定的产物是「为什么需要形式化」和「为什么不需要」。不需要时明确写出覆盖边界后停止。

## 2. 按问题选工具

按问题选工具，不按工具选问题。完整判据见[工具选择](references/tool-selection.md)。

- **事件顺序、交错、重试、协议**：对设计的小模型做模型检查，模型语言按项目可维护性选，不绑定某个厂商工具。
- **代码本身对所有输入的行为**（越界、溢出、不变量）：用能跑在该语言上的验证器或 SMT 支撑的检查器，直接在真实代码上验证。
- **该语言没有可用验证器**：说明这一点，用生成输入测试真实代码，不用手写模型冒充代码。
- **界不足、必须在每个规模成立**：用证明助手或精确证明义务，并接受更高的维护成本。
- **只要回归覆盖**：普通测试就是答案，记录它覆盖什么、不覆盖什么。

优先选项目开发者能自行安装、运行、锁定版本的工具；把选择理由写给用户看，并把工具与版本记入假设账本。安装或升级工具属于环境准备，按委托权限执行；无法安装时标 blocked 并写清缺什么，不静默换成更弱的检查再声称已完成。

## 3. 什么算好

- **忠于代码**。模型或证明的每一部分都指向审查者能打开的代码；验证当作一个不可分步骤的，在代码里就是一个不可分步骤；命名取自本仓库。
- **能够失败**。从没见过失败的检查证明不了任何事。对每条性质，在真实代码的坏变体上（去掉一个检查、调换一步顺序）展示它确实失败，并保留该故障暴露证据。
- **发现就是发现**。当前代码违反性质时，用代码自己的话报告反例，不削弱性质或模型来制造通过，也不在未被要求时改产品代码。
- **范围诚实**。写明验证了什么、在什么界和假设下、排除了什么。通过覆盖的是模型或界，不是整个系统。
- **不依赖工具也能读**。用一句平实的话写出性质与危害；反例讲成代码语言里的短步骤序列。
- **重跑便宜**。一条命令、可复现的工具版本、足够短的时间，让下一个执行者在每次相关改动上都愿意跑。
- **与代码同步**。记录每条检查覆盖的文件与函数、外部假设与依赖版本，以及最后一次确认「检查仍描述当前代码」的实际同步对象；commit 不能单独代表未提交的工作树输入。
- **不混淆四类结果**。形式模型通过不等于代码通过；定理编码编译通过不等于原定理成立；有限数值结果不是一般性证明；普通测试通过不是形式化验证。

## 4. 记录外部假设、版本与同步状态

按[假设账本](references/assumption-ledger.md)建立并随资产发行，至少记录：

- 外部假设与材料：引用的外部定理、规范、数据、生成器、公理，以及各自来源与版本；
- 依赖版本：检查工具、求解器、库、模型检查器、证明助手与标准库的实际版本；
- 实际覆盖：被检查的文件、函数、性质、界与输入域，明确写出未覆盖部分；
- 同步状态：最后一次确认检查仍描述当前代码的 commit、日期、运行的命令与结果，以及覆盖代码与验证输入资产（模型、harness、性质、配置）的路径/内容摘要（如 SHA256）；保存已暂存、未暂存及相关未跟踪输入的状态，实际读取的被忽略输入也不遗漏；
- 变化后的重验判断：哪些变化（工具或库升级、外部定义改动、输入数据更新、覆盖代码改动、界调整）会使旧结果失效。

工具或材料变化后，旧通过不再替新对象背书；同 HEAD 的工作树变化也使相关结果 stale。运行前后核对输入清单，只有当前对象经核验和执行且无未审变化才保存新同步记录；旧记录缺少实际输入时先标未核实。未知的版本或未读取的材料保持未核实，不按通过记录。

## 5. 审计编码声明与原问题的对应

按[对应审计](references/correspondence-audit.md)检查「原问题 → 编码定义 → 定理／检查声明」三者是否说同一件事：量词、假设、定义域、对象编码、边界与索引、是否悄悄加强或削弱了命题。审计结果逐条写出结论与证据位置。

以下任一情况不得记为「原定理成立」：

- 存在占位符、未定义的假设、被吞掉的公理或待办标记；
- 只有编译成功或构建成功；
- 只有有限数值试验、抽样或模型检查的界内结果；
- 编码声明比原问题更强、更弱或换了对象。

以上只能作为候选或草稿状态，交付时明确写出差距。

## 6. 生成项目本地 verify skill

写一个项目本地 skill，frontmatter 命名该区域并说明何时使用；没有 frontmatter 的说明不会注册。仅凭这个 skill，下一个执行者必须能判断一次改动是否触及被验证代码、运行检查、区分真 bug 与建模错误，并在改动是有意的时候更新验证。

把覆盖记录、同步对象（commit 及实际输入清单/摘要）、外部假设与依赖版本、对应审计结果和草稿状态写进该 skill，使用本仓库真实的命令、路径与名词，不留占位符。记录结构可用[检查记录模板](templates/formal-verification-record.md)。生成的资产如果在交付前从未被执行，标记为草稿，不宣称可用。

## 7. 交付前自证

像下一个执行者那样，按生成的 skill 在一个划痕改动上走一遍：该改动在真实代码里破坏该性质，检查必须抓住它。随后撤销划痕改动，确认检查回到起点：通过，或只在你将报告的发现上失败。抓不住破坏、或某步跑不起来时，修 skill 或验证本身，不修划痕改动来迁就。

自证同时核对这些内容：命令可复制执行、失败信息可读、反例能对应回代码、假设与版本与运行时一致。没跑过的步骤、没装成的工具、没读到的依赖一律标为未运行或未核实。适用范围有限但诚实的检查，好过假装完整的全链形式化。

## 8. 交接

告诉用户：验证了什么；用了什么工具、为什么；界与假设；检查在当前代码上发现了什么（用平实语言）；怎么运行；不覆盖什么。只在确实接近时建议第二个目标。需要把验证与变化的代码重新对齐时，指向 `maintain-formal-verification-skill`。

宿主中立：不写死任何特定宿主品牌、个人目录、固定模型或厂商专属命令；派发与独立复核按当前会话真实可用的能力决定，缺子代理时标 blocked，不以串行自查冒充独立复核。静态结构检查与一次安装成功只证明合同与可达性，不证明数学结论成立。
