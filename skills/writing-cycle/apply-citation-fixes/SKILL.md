# 显式应用引用修复

仅由用户显式调用。引用审计报告、父流程建议或用户曾授权审计都不构成本入口的调用与写入授权。本 Skill 不自动启动其他顶层 Workflow，也不以“元数据小改”绕过确认。

输入：用户指定的审计发现／报告（可为对话中的发现）、当前正文与 bib 文件、用户要处理的条目、现有约束（特别是 soft-only）、已有来源材料与资源预算。报告可以提供待处理问题，但不能替代当前原文和新的来源核实。

输出：确认前的精确修复方案，以及确认后的实际改动／未改动／未核实 Markdown 报告。只写用户明确批准的研究材料范围与已授权报告位置；未授权报告落盘则在对话返回。报告已有内容先读取，写前若变化停止覆盖。

## 1. 重读与核实

读取当前原始 bib、正文入口和全部实际包含材料，重建要修改 key 的全部使用位置及引用关系。包括附录、图注、脚注、讲稿／备注；保留非 LaTeX 原格式。对多 key、跨行、自定义引用宏、重复 key、同论文双 key、`nocite`、crossref／xdata 等依赖明确范围；无法确定影响集合就停止相关修复，不只改报告里列出的那一处。

读取 [来源核实方法](references/verification-methods.md)，按 SEARCH → VERIFY → RETRIEVE → VALIDATE → PROPOSE 核实原来源、每个字段与每处 claim；候选 replacement 无论是否已在 bib 中，都先独立核实身份与目标语境支持。新的审查使用 fresh、与作者／修订者分离的 reviewer，只给任务、原始路径／URL、客观定位、范围与约束；不提供旧审计结论、执行者推荐或摘要引导判断。reviewer 自己打开原始 bib、正文及被引论文。

预算耗尽或只获部分查询授权时，停止受限查询与 reviewer 调用，不扩大预算；保留已完成证据，逐项列出未查 key、引用位置与原因，相关补丁暂缓，交付部分报告，其余授权检查可继续。

无来源读取或独立 reviewer 能力时，指出未完成的轴和复核，相关补丁暂缓，给用户补证动作；不猜来源、不安装或配置环境、不请求超出授权的付费资源。已确认错误与未核实分别保留；“搜不到”不等于“不存在”。

完成条件：每项候选变更都有当前原文、全部影响位置、三轴证据或明确阻止应用的缺口，且实际约束已记录。

## 2. 展示精确 diff 与完整范围

将修复分为可以独立授权的方案组。每组列出：

- 问题、三轴原始证据与理由；
- 每个实际目标文件及位置、当前完整条目／句子与拟议内容；使用包含前后文的精确 diff，不能只说“更新作者”；
- bib、key、正文引用、claim 文字各自是否改变，以及全部受影响的引用位置；
- 依赖项、保留问题与写后复验范围。

key 更名／条目删除／重复合并必须连同全部相关正文引用及 bibliography 依赖作为一致性组展示；不能批准一半后制造未定义引用。用户只批准某一语境的改写时，不顺手改该 key 在其他位置的正确用法。

保留项目既有 key 风格、引用系统与编码；不批量整理无关条目。元数据只取已核实的来源值；replacement 必须展示已核实的新条目或现有条目与精确支持证据，待查候选不能进入可执行 diff。去除引用时同时处理剩余句子是否仍声称无依据的结论。

### soft-only 约束

继承报告及当前用户／项目的冻结要求，默认保留更严格的约束，不因调用 apply 自动解除。所有 bib 原样保留，含新增、删除、字段、格式、去重与 key 更名。

- KEEP：不改。
- FIX：报告元数据漂移仍未修复，不能靠改正文宣称字段已正确。
- REPLACE：只在出问题的位置收窄为原论文实际支持的表述。
- 已确认错误／虚构引用的 REMOVE：可展示正文删除该引用并撤回依赖的主张，或改用已核实且支持 claim 的现有 bib 来源；原 bib 保持不变。
- UNVERIFIED：等待补证，不从未核实推出删除必要性。

若还有“正文引用标记也冻结”约束，标记上述移除／换引用方案不可执行；不偷换为 bib-only 冻结。解除冻结须用户另行明确决定，并重新展示该范围下的新 diff 获授权。

完成条件：用户能逐组辨认确切改动、范围、依赖和残余问题；所有可执行内容都已展示，没有隐藏清理。

## 3. 等待明确授权

对每组询问“应用／拒绝／暂缓”，等待回复。用户调用本 Skill、“看起来不错”、旧报告上的历史批准、父流程让你修复都不能取代本轮精确 diff 之后的明确授权。

- 全部拒绝或暂缓：零研究材料写入，返回保留问题后停止。
- 部分同意：只处理被明确批准且依赖完整的组；拒绝／未回应的组保持原样。
- 一致性组只批一部分：暂停该组，解释断裂，展示可独立成立的新方案后再询问。
- 用户要求不同改法／发现来源不足：重新核实并展示新 diff，旧批准不覆盖变化后的内容。

完成条件：每组都有明确决定，可执行范围仅包含当前 diff 的有效批准。

## 4. 写前重读与冲突停止

在任何研究材料写入之前，再读取所有目标文件、相关 bib、正文入口／包含关系、全部受影响引用以及支撑方案的原始来源；对照展示时的实际内容和约束，而不是只信旧行号或报告。以原文与精确 diff 完成比对；不生成额外 SHA／digest／receipt 或内容固定协议。目标若是符号链接，检查实际写入目标也在授权范围内。

任何条目、句子、文件包含关系、引用集合、来源证据、目标路径或冻结约束变化，或者存在重复 key／无法识别的修改影响：停止整批尚未执行的写入；报告冲突并重建 diff，重新获授权。文件新出现、被替换或相关正文新增引用也算变化。不能把变更静默合并进已批准补丁。

完全匹配后仅应用批准组的精确变更，保持其他字节与段落。每次实际写入前再次确认该文件仍匹配预期；多文件变更不是天然原子操作。中途冲突／写入失败立即停止后续写入，列出已完成和未完成文件、可能的引用断裂；不声称整批成功，不用自动回滚覆盖外部变化。回退也须展示当前状态下的精确 diff 并获授权。

完成条件：实际写入能逐项对应批准内容，或者已明确停止并报告部分状态，无越界修改。

## 5. 写后复验与交付

重读最终实际文件，不以写工具成功作为正确性证明。重建所有受影响 key 与原／新来源的引用集合；删除、换 key、合并、共享 bib 元数据变化要覆盖所有相关正文，局部句子变化也检查同句其他引用。静态检查未定义 key、重复／冲突 key、bib 字段分隔／括号／特殊字符、旧 key 残留、`nocite`／crossref／xdata 依赖，以及是否出现授权外改动。

用新的独立 fresh reviewer 对实际最终材料重跑三轴：身份、元数据、每一处受影响语境；包括修改后新出现或重定位的引用、被替代来源剩余的其他用法，以及删除引用后句子是否仍有证据支撑。它只接收原始最终路径／URL、任务和客观范围，不接收旧结论或“已经修好”的解释；重新打开对应原始论文而不是接受先前报告。依赖冻结而仍有元数据错误时如实保留，不把冻结当核实通过。

复验有错误、网络失败或 reviewer 不可用：报告已写入但未通过／未完成复验的具体范围，停止，不自动继续修复或回滚。新修复需重新走 diff 与授权。无需自动编译；静态引用检查不等于排版、页数和完整编译通过，若用户需要该层验收，明确列为后续另行授权事项。

以自然 Markdown 返回：

1. 实际应用的组、文件与最终 diff；
2. 拒绝、暂缓、无法核实、约束下不能应用、冲突／失败项，分别列明；
3. 写后覆盖的全部 key／引用位置及三轴证据、来源定位、独立审核状态；
4. 仍存在的问题与具体补证／人工检查事项。

仅当所有实际变更及全部受影响引用复验完成才称“已应用并复验”；不要把部分同意说成全部问题解决。交付即停止，不自动渲染、同步、投稿、编译或启动其他 Workflow。
