# 叙事、结构与演讲准备

本方法合并 ARIS paper-slides 与 Orchestra presenting-conference-talks。选大纲时先用“类型与结构”，逐页起草时用“表达与交付”，系统论文再用“Systems 分支”。所有示例槽位都必须由用户论文支持；没有某类实验就调整大纲，不补造内容。

## 类型与结构

| 类型 | 常见时长 | 参考逻辑页数 | 内容深度 | 每页节奏参考 |
|---|---|---|---|---|
| poster-talk | 3–5 分钟 | 5–8 | 问题、一个方法、一个关键结果、结论 | 30–60 秒 |
| spotlight | 5–8 分钟 | 8–12 | 问题、核心方法、主要结果 | 30–45 秒 |
| oral | 15–20 分钟 | 15–22 | 动机、设计、评估、分析与局限 | 45–90 秒 |
| invited | 30–45 分钟 | 25–40 | 背景、深入方法、多组结果与讨论 | 60–120 秒 |

这些是规划启发，不能相互强制：oral 约每分钟一页、spotlight 约每分钟 1.5 页只是起点。具体时长优先于类型标签；例如 15 分钟 spotlight 应先确认实际限制，不硬塞进 8 分钟模板。扣除 Q&A、演示及转换时间后分配各页，不用页数推导“已满足时长”。

### Poster-talk：5–8 页结构

| 页 | 目的与原材料 |
|---|---|
| 1 | 标题、作者、机构：来自真实元数据；匿名时按用户规则处理 |
| 2 | 问题及重要性：引言；可用一幅已有动机图 |
| 3 | 核心洞见：一句 thesis；极短报告可与问题页合并 |
| 4 | 方法概要：一页架构或机制图；按论文解释 |
| 5 | 最重要结果：一幅有单位、baseline、范围的图或小表 |
| 6 | Takeaway 与用户提供的论文/代码链接；没有链接就省略 |

证据确实需要时扩展至 7–8 页，不添加无依据的“精彩结果”。最后一页承担结论而非空泛“谢谢”。

### Spotlight：8–12 页结构

| 页 | 目的与原材料 |
|---|---|
| 1 | 标题与作者 |
| 2 | 具体、可界定的问题 |
| 3 | 现有方法的限制与动机；若量化，给原文依据 |
| 4 | 核心洞见/thesis |
| 5 | 系统或方法全景图 |
| 6 | 核心机制/设计亮点 1 |
| 7 | 关键设计亮点 2；只有一个亮点时不凑数 |
| 8 | 简要评估设置：baseline、workload、metric |
| 9 | 主要结果及带范围的结论 |
| 10 | 消融/分解：仅论文确有该证据时 |
| 11 | 贡献回顾及必要局限 |
| 12 | 结束、已核实链接与 Q&A |

压缩到 8 页时合并问题/动机与设计，保留结果的测试条件。不能把结果中不支持的范围藏到 backup 后不在主讲提醒。

### Oral：15–22 页结构

| 页 | 目的与原材料 |
|---|---|
| 1 | 标题、作者、真实 venue |
| 2 | 可选 roadmap：给听众问题地图，而非照抄论文目录 |
| 3 | 问题背景及领域意义 |
| 4 | 具体挑战和约束 |
| 5 | 动机：当前方法/系统的缺口 |
| 6 | 核心洞见与 thesis |
| 7 | 方法/系统概要，优先使用论文 hero figure |
| 8 | 核心组件 1 具体 walkthrough |
| 9 | 核心组件 2 |
| 10 | 核心组件 3 或与理解相关的方法细节 |
| 11 | 设计替代方案及取舍 |
| 12 | 实现重点（论文确实报告的工程细节） |
| 13 | 评估设置：testbed、baseline、metric 与实验范围 |
| 14 | End-to-end 主要结果 |
| 15 | 按 workload 或条件的结果分解 |
| 16 | 消融：哪些设计带来何种证据 |
| 17 | Scalability（仅已有测量支持）或关键局限 |
| 18 | Systems demo/截图/录屏（仅有可用、获准资产） |
| 19 | 可选简短相关工作定位，或分析/局限 |
| 20 | 总结：问题、方法、证据与贡献 |
| 21 | 局限及已标为计划的未来问题 |
| 22 | 结束与真实论文链接；停留供 Q&A 使用 |

ARIS 强调短 talk 不设孤立 Related Work 页，Orchestra oral 模板保留简短定位。这里按听众理解需求选择：通常把必要引用融入问题/方法页；确需比较脉络才单设，invited 可展开。设计组件、scalability、demo 均为条件槽位，不是每篇论文必须拥有的研究结果。没有适用项时经大纲确认删减，不强制追求 22 页。

### Invited：25–40 页结构

在 oral 结构上按听众与证据增加：

1. 领域全景、历史进展及必要术语，让非本领域听众进入问题。
2. 多个机制/系统具体请求 walkthrough；每个过程先说明输入、约束与想回答的问题。
3. 深入方法、推导、设计替代方案和权衡，而非增加文字密度。
4. 多组评估及额外分析，保留测试条件和失败/不适用范围。
5. 只有已有获准材料时使用多个 demo；每个留备用静态路径。
6. 更广影响与未来方向明确标为讨论/计划，不升级为已证实结论。
7. 准备不计入主讲时间的 backup：额外评估、算法细节、证明或常见 Q&A 证据。

## 表达与交付

### 先 why，再 what

演讲是时间上的故事，不是把论文切成页面。先让听众理解为什么值得关注，再展示做了什么。开场用论文能支持的问题、观察或具体情形，避免开口就逐条宣布“本论文的三项贡献”。不能为了 hook 编造规模、用户故事或挑衅性数字。

逐页要求：

- 一个主旨；两件事需要分开时回到大纲确认，不在视觉精修中偷偷拆页。
- 标题尽量 claim-first，英语可参考不超过八词；精度、单位和限制语比机械字数更重要。
- 常规页 3–5 条短要点，尽量不超过六行、每行八个英语词；中文按可读性判断，不照搬空格分词。长解释留给讲稿。
- 图页让图占主要面积，约 60% 或以上为起点；要点用于注释，不能挤成论文段落。
- 强调核心数字，但标清均值/最好一次、比较对象、单位、百分点/相对变化和实验范围。
- 复杂公式、架构或算法逐步 reveal。先解释符号/组件，再揭示联系，最后说该图支持哪一结论。
- 删除空泛赞词和模板腔，用具体条件与机制替代“革命性”“全面领先”。

### 三层预告—展开—回顾

Orchestra 归于 Mike Dahlin 的 layered approach：

1. **Talk**：开头说明要回答的问题 → 主体展开 → 总结同一 thesis。
2. **Section**：短章节导语 → 相关内容页 → 本节 takeaway；让听众知道为何进入下一节。
3. **Slide**：先说本页主旨 → 指向证据 → 转场解释下一页的因果关系。

这是节奏指导，不要求每页重复三句套话；短报告可省独立 outline 页。该方法归属由上游提供；此资源不依赖或复制外链 Dahlin PDF。

### Notes 与 script 分工

每页 notes 是 2–4 句提示：要说什么、时间提示、下一页转场；图页写明指向的线/柱/组件。每页 script 是实际可朗读的完整段落，有起止时间、停顿和指图提示，不是把 notes 换标题后重复。

累计时间表的总秒数应符合预算。按语言与讲者实际速度估计字数，注明只是估计；讲者真人计时排练才能确认。标题页可留给主持介绍，但未知主持人名字不能填入。结束页只在真实有链接/QR 时才说“屏幕二维码可获取代码”。

### Q&A：保留八类准备问题

每题答案读取具体原文，给证据位置或明确未知；不为“准备充分”补做实验。

1. **最强 baseline**：哪些条件下有差异？具体数字与比较设置是什么？
2. **主要局限**：哪些场景未测、失败或代价显著？诚实限定。
3. **计算/实现成本**：论文是否报告训练、推理、内存、网络或人工成本？没有就说未测。
4. **跨域泛化**：论文讨论和实际评估各自到哪里？理论设想不等于观察。
5. **意外发现**：只选论文真实报告的现象，不虚构“我们惊讶地发现”。
6. **敏感性/设计选择**：使用已有消融或分析；没有消融就不声称验证了原因。
7. **下一步**：来自论文未来工作或用户提供的计划，明确尚未完成。
8. **领域特有问题**：Systems 的故障模型/负载/一致性，ML 的数据泄漏/seed/公平比较，理论的假设/反例/证明范围，按论文选择。

## Systems 分支

### Demo 与备用路径

若已有获准 demo/录像，规划现实负载下的演示，而非把 toy 画面伪称线上测量。现场 demo 必须有录像或静态截图备用，notes 写明失败后何时切换。录制、运行系统、接入远程服务不包含在默认生成权限中；无现成资产时报告“demo 未提供”，可改为论文支持的静态流程图，不声称录屏已生成。

### Architecture walkthrough

从一个具体请求出发：输入 → 组件处理 → 通信/数据流 → 输出。逐步高亮当前组件，解释设计原因、替代方案及 trade-off。Beamer 可使用 `\only` / `\onslide`；PPTX 可用用户支持的动画或连续静态步骤。示意图标明为机制说明，不冒充原始测量图。

### Evaluation highlights

选择 2–3 幅最能回答研究问题的真实图，而非只挑最大提升：保留典型情形、反例及测试限制。先说带条件的 takeaway，再展示图的证据（“在该 workload 的三次测试均值下降……”）；箭头/圈注只强调已有数据，不改变轴、图例或尺度。额外结果放 backup，但不能把推翻主讲概括的结果隐藏。

## 视觉起点与常见问题

颜色是美学建议而非会议官方规定。可用黑/深灰加一个强调色；如用户要求 venue 风格，上游给的 USENIX 深蓝/红、ACM 蓝/深灰、NeurIPS 紫/金、ICML 青/橙仅作候选。用户模板与实际官方规定有冲突时由用户决定；无获准网络能力就注明未核对最新官方要求。

标题、正文、注释按实际渲染与投影距离判断。PPTX 正文可从 24pt 以上、标题 28–44pt 起步；Beamer 的 pt 与大尺寸 PPTX 不可直接等比套用。两种来源字号建议冲突时以实际渲染可读性与用户模板为准，参见 [视觉精修方法](visual-polish.md)。

| 问题 | 方法 |
|---|---|
| 时间不够 | 优先删细节、保留每个关键论点的一幅证据图；更改大纲先确认 |
| 页面像论文段落 | 改为短要点；口语解释留给 script；限制语仍可见 |
| 设计部分听众迷路 | 加架构全景回顾和具体请求 walkthrough |
| 结果页过载 | 主讲 2–3 幅关键图；其余 backup，主结论的反例仍须披露 |
| Notes 过长 | 收敛到提示、时间、转场；全文保留在 script |
| 图不可读 | 使用获准高分辨率图或裁出相关区域并标明裁切；不能重造数据 |
| Beamer 编译失败 | 查实际日志和已授权图路径；只修输出源码，不安装缺包 |
| PPTX 与 Beamer 视觉不一致 | 逐页比较实际渲染，调整字号和框大小，保持图片比例及内容 |

## 排练 handoff

建议用户用逐字 script 计时朗读，检查每个转场及总时长；再用 notes 做不逐字阅读的排练。与同事 dry run，验证开场问题、最终 takeaway、字体、视频切换和备份。记录实际排练速度与需删减页，再由用户决定是否授权下一轮。生成计时表不等于真人排练通过。
