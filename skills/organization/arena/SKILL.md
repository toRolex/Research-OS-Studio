# Arena

一次 arena 是对同一任务的 N 个独立候选竞争：各自完整作答，交叉评判与主编排者按预先声明的 rubric 逐项比较，主编排者综合两方结论后选基座并手工整合落选候选的可取部分，再验证整合结果。开始前在 todolist 里为每个阶段（Frame、Fan-out、Cross-judge、Pick、Graft、Verify）各开一条，逐条跟踪后才启动候选。

## 委托继承

Gates: none

由 `/research-os` 级联进入时，本次 arena 继承调用者的研究委托：目标、权限、研究额度与完成条件沿用，不重复请求批准；只有目标替换才停下确认。独立调用时，以用户给定的任务及其明确范围为授权；在 Frame 阶段写明候选数与输出位置。用户未给候选数时，默认两个；确需覆盖多个设计方向时再增加并说明理由。输出位置优先沿用用户指定位置，否则使用本次工作区内不覆盖既有材料的独立目录。无需先 setup。

**子代理前提**：fan-out 与交叉评判都以当前会话确实可调用子代理工具为前提。缺该能力时本能力标 blocked 并写明缺口，只给只读建议（如何自行做有界比较或该直接点名哪个单能力），不由编排者自己串行扮演多个候选，也不把串行代跑记成 arena 已执行。本能力独立于其他组织能力，不要求先运行任何兄弟能力。

## Phase A: Frame

所有候选拿同一份 prompt，prompt 就是合同。

1. 写明每个候选要产出的 artifact 是什么、交付到哪。
2. **先声明 rubric**：3–6 条针对本任务、可具体打分的标准，在候选运行之前写下来。它是 Pick 阶段的工具；候选只看任务本身，不看 rubric。
3. 定候选数与执行者。执行者按研究项目角色表（`.agents/research-os-models.md` 的 `Role:` 行）或当前会话实际可用的子代理能力解析，核实可用后再派发。没有文件或角色行时可使用实际可用的模型与 thinking，明示缺失及回退来源。明确选定的模型不可用或 thinking 不支持时，先核对有效原委托是否明确允许相应替代：已授权替代可在当前可用性、档位、费用与范围限制内继承，并明示授权来源及实际派发值；未授替代权则先停该派发，请用户确认，不以一般任务或剩余额度推导任意替代。行重复或格式错误时停下澄清，不静默改配置，不编造 slug，不固定品牌或个人默认。工作是多方向设计而非判断敏感时，可用同一模型多次；覆盖多个设计方向时增加候选数。
4. 给每个候选自己的输出位置（可行时各一个 git worktree，否则同一父目录下彼此独立的 `candidate-<n>/` 目录）。候选之间不共享写入，不读到彼此输出——先隔离，再比较。

## Phase B: Fan-out

在同一条消息里并行派发全部 N 个子代理，每个拿到同一任务原文、共享输入材料路径、自己的输出路径，以及「产出 artifact + 一段理由，写明考虑过并拒绝了哪些替代方案」的指令。

候选完成前不启动评判。某候选没有产出时，用 N-1 继续，如实记录 dropout 与可能原因，不补造候选。

## Phase C: Cross-judge

全部候选完成后，选一名交叉评判者：尽量取与主编排者不同的模型或家族（按实际可用能力解析，做不到时声明同源），派一个只读子代理。它拿到 rubric 与各候选的路径标签（不透露作者与派发顺序），对每条标准逐项打分并推荐基座及理由。候选还在写的时候不要派评判者；评判者与主编排者的阅读可并行。

## Phase D: Pick

主编排者**完整阅读每一个候选全文**后才能选。对照 rubric 逐项打分，不做整体印象判断；把独立评判的打分与推荐摆在一起比较：一致则确认基座；不一致说明其中一方有偏差或 rubric 有歧义，先读两份理由再裁决，必要时锐化 rubric 重评。两个候选难分上下时，选未来维护者更容易扩展、边界更干净的那个。

## Phase E: Graft

对每个落选候选再走一遍，挑值得移植进基座的东西（通常每个一到两处，不是大半篇）。每处移植都手工改写融入基座，让结果保持在一个连贯的心智模型下；不机械拼接段落。候选收敛到同一形状是强一致信号，如实记录共识并交付共识形状，无需 graft；候选严重发散说明 Frame 不足，回到 Phase A 重框重跑，不取折中平均。

## 数学整合后的重查

候选是数学论证、推导或证明方案时，graft 完成后必须对整合结果整体重查一遍：假设是否仍然成立且被声明、记号是否全篇一致无冲突、依赖是否闭合（每个被引用的引理/事实在结果内部有出处）。单段正确不等于拼合正确。

**候选胜出不等于命题成立**：arena 的胜出、评判一致或共识形状只是候选之间的相对结论；原命题是否成立由 Verify 及后续独立验证回答，不因多候选竞争而自动成立。

## Phase F: Verify

像验证任何其他产出一样验证整合产物：区分已验证与未验证，写明覆盖范围与假设。验证发现 arena 漏掉的问题时，要么 Phase A 框错（重框重跑），要么某候选已捕获而你漏了 graft（回 Phase E）；不掩盖、不放宽标准制造通过。

## Outputs

一个整合产物，附一份简短 synthesis note：基座及选择理由、交叉评判结论、每处 graft 及其来源候选、被拒绝的部分及原因、收敛或 dropout 情况、验证结果与未验证项。
