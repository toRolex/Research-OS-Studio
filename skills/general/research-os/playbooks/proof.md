# proof

从已有数学成果、证明材料或推广障碍继续研究。保持原委托目标；局部 obligation 帮助拆解工作，但不能替代或暗中缩小总目标。本配方按当前证据选择和交替方法，不是一串每项必经的阶段。

## 先读

1. 读取[研究委托合同](../references/mandate.md)，以用户原问题确定目标、授权、额度和停止条件。
2. 直接核对原命题、定义、量词、假设、依赖来源、已有推导/证明、计算和审查产物、失败路线与开放义务。旧总结是线索，不替代原文；不把尚未验证的结果当事实。区分原问题与推广问题。
3. 只读当前证据需要的能力正文与其共置参考/模板；每个能力仍按自己的职责交付。证明审查分支读取 `proof-review`；只在确需第二意见、符号审计、边界回归或 Lean 检查时，按该 Skill 的条件索引读取相应数学方法与交接模板。缺少 `proof-review` 只阻塞独立证明审查及其专属方法分支，不阻止可独立完成的推导、构造或计算。

## 总控与角色

本次 `/research-os` 委托是唯一总控：目标、写入范围、额度、授权继承、目标替换和停止规则以 [mandate.md](../references/mandate.md) 为准。内部能力交接、重试、暂停和恢复不重开或重置额度；长任务用 [continuation](continuation.md) 收束或续接，用 [pickup](pickup.md) 重查原始产物与开放义务。只有整体材料确需一轮有界 review—repair—re-review 时，才按 [improvement](improvement.md) 组合独立能力 `research-improvement`，不把它变成证明的固定前置阶段。

Role: orchestrator

保持原目标、证据/方法记录和总额度；按当前缺口选择下一项能力。

Role: prover

在其声明范围内推导、构造证明或执行获准修复；交付具体命题、依赖和未解义务。

Role: reviewer

对原命题及其依赖作 fresh 只读审查；自查不冒充独立审查。

## 按证据选择方法

每次获得新材料、遇到缺口或发现方法失效后，判断哪类工作最能回答原问题；可以交替、并行或返回已走过的路线。下面是可组合分支，不规定统一顺序，也不要求每次全部调用。

| 当前需要 | 使用已有能力 | 保持的边界 |
| --- | --- | --- |
| 将代数关系、记号或局部恒等式化为可核查推导 | `formula-derivation`；需要严格证明时另由 `proof-writer` 处理 | 公式推导不自动等于证明；推导与证明构造各守其职责。 |
| 寻找证明、显式构造、特殊情形或反例 | `proof-writer`；保留其 proof package 与失败记录模板 | 固定原命题及假设；构造物须检查是否满足原问题条件。 |
| 局部精确/符号/数值计算有望区分候选或暴露缺口 | 依实际问题做有界计算；需要项目内可重跑代码检查时，使用 `create-verification-skill` 或变化后的 `maintain-verification-skill` | 记录输入、覆盖范围与假设。有限计算可发现线索或反例候选，不证明未覆盖的无限命题。 |
| 多条实质不同的路线需要并行覆盖 | `swarm`；需要让同一任务产生并比较多个完整候选时用 `arena` | 复用各自的分片、候选、证据和比较合同，不另造并行机制；缺少所需子代理能力时只阻塞该分支，不由编排者串行扮演。候选胜出或共识不证明命题。 |
| 需要证明层的义务审查或更广的独立挑战 | 数学证明义务用 `proof-review`；多 reviewer 的研究挑战与主审综合用 `interrogate` | 按需读 proof-review 的审计、独立审查、记号、Lean 与交接参考；保持只读与独立性，审查报告是 findings，不是修复授权或数学证据本身。 |
| 现有 finding 需要有限修改 | `proof-repair` | 以 finding 和原命题为界；修复者不取代 reviewer，不得静默改假设或结论。独立复审能力缺失时报告未完成，不声称已通过复审。 |
| 形式化可能显著检查全称性质、形式模型或定理编码 | 无既有项目检查时评估并按需用 `create-formal-verification-skill`；资产随对象变化时用 `maintain-formal-verification-skill` | 评估并尝试有价值的范围，不强制全链形式化。审计形式化陈述与原问题、外部假设及实际覆盖；普通测试足够时说明理由，不升级工具链。 |

以上是彼此独立、按 slug 发现和安装的能力；Skills CLI 不会替用户解析或安装跨 Skill 依赖。进入分支前确认所需 slug 已安装并读取其完整正文与共置资源；缺少某能力只阻塞依赖它的分支，并如实标注，不以自审、串行扮演或开发者目录补位。不要把 Skill 里的 prompt 或内部流程复制成第二套工具合同。

## 义务、方法与失败记录

- 对每项局部 obligation 记录准确命题、假设、依赖、现有证据和关闭条件，并说明它如何支持原目标。比较辅助引理的适用域、假设和结论强度；等强未证引理仍是开放义务，改名或移到依赖图里不算进展。
- 先比较真正不同且适合当前目标的方法族，例如结构/归纳、估计/变换、显式构造/反例、精确/数值计算；按需扩展、交替或放弃，不设固定数量，不把改名或换符号算成新方法。保留实际考虑或执行的方法族及其理由。每条失败路线记下尝试到的具体步骤、失败原因/证据，以及什么新证据、新工具或新机制足以支持重开；没有新信息时不重复原样尝试。方法记录沿用 proof、derivation、review、repair 各自的包与模板，不创建新的控制账本。
- 需要新的审查、计算或独立挑战时按证据加入；新结论回到原命题与依赖核对。某个局部路线受阻，只停止或改换该路线，不把它升级成整个委托的停止条件。

## 反例与目标边界

严格反例若逐项满足原命题假设并否定原结论，就是对原问题的有效回答；准确说明它反驳的结论和覆盖范围，不为保留预期答案而隐藏它。数值异常、浮点近似或有限采样结果仍是候选，直到有针对原命题的严格论证或可复核证书。构造的反例也须独立核对定义与条件。

改变路线、局部 obligation 或辅助命题可在原目标内进行。若要替换主要目标、结论、范围或交付物，按委托合同等待用户确认；等待只阻塞目标替换分支，其他原目标工作继续。不得以推广问题、等强引理或较弱结论静默替换原问题。

## 完成与停止

报告原目标及已回答部分、每项结论的来源/推导/计算/审查/形式化证据、适用范围与假设、未验证部分、失败路线和开放义务。区分严格证明、严格反例、候选、数值结果、审查判断与形式化/程序运行结果；编译通过、模型共识或有限计算都不单独代表原数学命题成立。

按[研究委托合同](../references/mandate.md)的完成与停止条件收束。委托写域内可直接创建新研究文件；阶段切换和已授权额度内的重试不重新索权。proof-writer、formula-derivation 与 proof-repair 各守其构造、推导、finding 修复职责；改变原命题或假设须先获用户确认，proof-repair 的编译命令与副产物须落在委托授权内。proof-review 每次 fresh 读取当前材料并保持只读。旧长期证明控制器已删除，任务续接、交接与停止由本委托及其交接配方管理。

案例只提供方法启发，不认证候选证明，也不据案例声称任何证明有效。
