RO Research OS 双版本指南

两个 Research OS，到底怎么用？

你期待的是像 ARIS 那样的纯 Skill 仓库。当前现实是：两个版本都包含 Skills，但也包含 Python CLI、contracts、validators 和安装逻辑。本教程不讲架构黑话，只带你跑通。

帮我选择版本 → 直接学 Studio
SResearch OS Studio更产品化，适合从零开始
01request + SHA-256先固定输入文件与摘要
02统一 workflow后续命令保持一种形态
03Publication由用户确认后冻结
RResearch OS功能更宽，适合兼容与诊断
01普通输入文件路径直接作为命令参数
02专项 CLI每项工作流参数不同
03发布工具提供更多底层命令
先记住这一件事

两个项目都安装同一个命令 research-os，版本号也都是 0.1.0。不要把两者同时全局安装；旧版用仓库内 uv run，Studio 才使用全局命令，最不容易混。

它不是纯 Skill 仓库

ARIS 更像“把操作说明交给宿主 Agent”。当前 Research OS 则把研究协议和确定性程序一起打包。Skills 告诉 Agent 怎么思考，CLI 和 validators 负责固定输入、检查结构、保存证据。

Skills：研究操作说明

Claude Code 或 Codex 读取 SKILL.md，知道某个 workflow 应如何推理、何时停止、产生什么 Artifact。

CLI：确定性骨架

research-os 负责安装资源、调用 workflow、检查文件、构建报告和冻结 Publication。

Artifact：步骤间交接

每一步把结果写成 JSON 或其他固定文件。下一步只读取你明确指定的输入，不会自己偷偷推进。

Skill：怎么做 + CLI：怎么固定和检查 + Artifact：留下什么

Research OS Studio

建议先学这个
1

安装 Studio CLI

在 Studio 仓库中把工具安装到 uv 的独立 tool 环境。完成后，终端中可以直接使用 research-os。

Terminal · 安装 Studio
cd "/Users/rolex/Documents/Codes/githubProject/MyProject/Research OS Studio"
uv tool install .
research-os --help
看到帮助列表就成功

应能看到 workflow、validate、validate-repository、validate-ports 等命令。

2

创建科研项目并安装 Skills

这里创建的是你的研究工作区，不是 Research OS 源码仓库。setup 会写入 Core、模板和 Agent 可见的项目级 Skills，不修改项目原有依赖。

Terminal · 创建目标项目
PROJECT="$HOME/Documents/my-research-project"
mkdir -p "$PROJECT"
cd "$PROJECT"
git init
research-os setup-research-os --project "$PROJECT"

安装后先查看目录：

Terminal · 检查安装结果
find "$PROJECT" -maxdepth 2 -type d | sort
3

从模板创建研究问题

Studio 不从随意的一段文字直接开始，而是先创建 typed JSON Artifact。请编辑问题、边界、成功标准与预算。

Terminal · 复制输入模板
cd "$PROJECT"
mkdir -p inputs requests reports
cp templates/outer/research-charter.input.json \
  inputs/research-question.json
open -e inputs/research-question.json
inputs/
research-question.json
{
  "contract": {"name": "research-os/artifact", "version": "1.1.0"},
  "target": {"kind": "git", "path": "inputs/research-question.json"},
  "type": {"name": "research-question", "version": "1.0.0"},
  "spec": {
    "question": "我的研究问题",
    "boundaries": ["不超出这个范围"],
    "success_criteria": [],
    "budget": {},
    "invariants": []
  }
}
4

固定输入并创建 request

先计算输入文件摘要。request 相当于一张“本次 workflow 工单”：指定准确输入、输出位置和报告位置。

Terminal · 计算 SHA-256
cd "$PROJECT"
shasum -a 256 inputs/research-question.json
Terminal · 创建并编辑 request
touch requests/charter.json
open -e requests/charter.json

把下面的 JSON 粘贴到新文件，替换 SHA-256，然后保存：

requests/
charter.json
{
  "inputs": [
    {
      "path": "inputs/research-question.json",
      "sha256": "把这里替换成上一步输出的 64 位摘要"
    }
  ],
  "output_path": "charter.json",
  "report_path": "reports/charter.json"
}
首次运行后不要原地覆盖旧输入和产物

修订时保留旧文件，新建 inputs/research-question-v2.json，同步修改其中的 target.path 并计算新摘要；再新建 requests/charter-v2.json，把输出改为尚不存在的 charter-v2.json 和 reports/charter-v2.json。

5

运行第一个 workflow

你可以走 CLI，也可以在安装了 Skills 的 Claude Code 中显式调用。第一次建议 CLI，错误更容易看懂。

Terminal · CLI 路线
cd "$PROJECT"
research-os workflow research-charter \
  --project "$PROJECT" \
  --request requests/charter.json
Claude Code · Skill 路线
/research-charter

使用当前项目的 requests/charter.json 作为本次请求；
核验输入路径和 SHA-256，严格使用其中的 output_path 与 report_path；
若无法执行，停止并说明原因，不自行更换路径。

Skill 路线不会自动继续到下一 workflow。以下验收命令适用于实际输出为 charter.json 和 reports/charter.json 的情况；如果 request 使用其他路径，请同步替换。

6

验证并人工检查

Terminal · 验证 Artifact
research-os validate --project "$PROJECT" charter.json
open -e "$PROJECT/charter.json"
open -e "$PROJECT/reports/charter.json"
Validator PASS ≠ 研究正确

PASS 只表示结构、路径、摘要和引用满足契约。你仍要阅读内容，再决定接受、修改、停止或调用下一步。

7

继续外循环

后续仍使用同一种命令形态：准备新 request，把 workflow 名换掉。系统不会自动接受前一步输出。

research-charterresearch-literatureresearch-gapresearch-idearesearch-noveltyresearch-reflect
Terminal · 通用命令模板
research-os workflow <workflow-name> \
  --project "$PROJECT" \
  --request requests/<request-name>.json

Research OS（旧版）

兼容 / 高级路线
1

在源码仓库同步环境

旧版最稳妥的用法不是全局安装，而是在它自己的仓库里用 uv run。这样即使 Studio 已全局安装，也不会调用错版本。

Terminal · 准备旧版
OLD_REPO="/Users/rolex/Documents/Codes/githubProject/MyProject/Research OS"
cd "$OLD_REPO"
uv sync --frozen
uv run --offline --frozen research-os --help

如果首次同步后 --offline 仍提示缓存不完整，暂时去掉 --offline 再运行。

2

创建目标科研项目并投影 Skills

Terminal · setup
PROJECT="$HOME/Documents/my-research-project-classic"
mkdir -p "$PROJECT"
cd "$PROJECT"
git init

uv run --directory "$OLD_REPO" --offline --frozen \
  research-os setup-research-os --project "$PROJECT"

这里使用 uv run --directory "$OLD_REPO"，所以你不必每次手动切回旧版仓库。

3

用普通 Markdown 写研究问题

旧版入口更直接。创建一个 question.md，不需要先写完整 typed JSON。

Terminal · 创建问题
cat > "$PROJECT/question.md" <<'EOF'
# 研究问题

我想研究：在明确的数据集与预算下，方法 A 是否优于基线 B？

## 边界
- 不扩大数据集
- 不改变评价指标

## 成功标准
- 结果可复验
- 所有结论有对应证据
EOF
4

生成 research charter

旧版每个 workflow 都有自己的参数。这里明确指定输入、输出 Artifact 和执行报告。

Terminal · 第一个 workflow
mkdir -p "$PROJECT/artifacts" "$PROJECT/reports"

uv run --directory "$OLD_REPO" --offline --frozen \
  research-os research-charter \
  --project "$PROJECT" \
  --input question.md \
  --output artifacts/charter.json \
  --report reports/charter.json
5

验证并查看 catalog

Terminal · validate + catalog
uv run --directory "$OLD_REPO" --offline --frozen \
  research-os validate \
  --project "$PROJECT" \
  artifacts/charter.json

uv run --directory "$OLD_REPO" --offline --frozen \
  research-os catalog
6

下一步先看帮助，不要猜参数

旧版没有统一 request 接口。每个命令的参数不同，所以先运行该命令的 --help。

Terminal · 查看专项帮助
uv run --directory "$OLD_REPO" --offline --frozen \
  research-os research-literature --help

uv run --directory "$OLD_REPO" --offline --frozen \
  research-os design-experiment --help

uv run --directory "$OLD_REPO" --offline --frozen \
  research-os math-proof --help
7

什么时候才需要旧版的高级命令

只有当你明确需要下列能力时，再深入旧版；新手不用一次学完。

prepare-local-cpuexecute-local-cpuexecute-sshexecute-slurmrender-*-manuscriptrelease-check
不要因为命令多就默认选旧版

更多命令意味着更强的诊断能力，也意味着更多参数和更高学习成本。

真正的使用心法

Research OS 不是“按一下按钮自动完成科研”。无论使用哪个版本，都按三个由你控制的阶段工作。

外循环

决定研究什么。

  1. 固定问题和边界
  2. 整理你提供的文献
  3. 识别 gap
  4. 产生并评估 idea
  5. 由你决定继续或停止

内循环

实验、分析和 Claim。

  1. 设计实验
  2. 准备环境
  3. 运行并保存失败现场
  4. 分析固定结果
  5. 判断证据支持什么

发布循环

冻结可复验成果。

  1. 选择 Artifact 和稿件
  2. 检查成员集合与摘要
  3. 核对最终 manifest
  4. 由用户精确确认
  5. 生成不可覆盖 Publication

最容易踩的坑

多数困惑不是你不会用，而是两个版本共享名称、文档又使用了不同操作模型。

×

同时全局安装两个版本

两者都叫 research-os 0.1.0。全局只保留 Studio；旧版固定用 uv run --directory "$OLD_REPO"。

×

把 workflow 当自动流水线

每一步完成后都会停止。你必须读结果、验收，再显式调用下一步。

×

把 validator PASS 当科研结论正确

Validator 检查结构和固定关系，不判断创新性、统计意义或学术价值。

×

Studio 修改输入后继续用旧摘要

每次修改输入都要重算 SHA-256，并更新或新建 request。

×

在两个版本间复制整个 .research-os

安装 manifest、contracts 和 Publication 语义不同。不要做原地混合升级。

×

期待它自动联网找文献

当前 Studio 的 literature workflow 整理你固定提供的文献，不承诺自动互联网搜索。

你可能还会问

这些答案用于决定日常怎么做，不展开内部实现。

我只想在 Claude Code 里用 Skills，不想记 CLI，可以吗？
可以优先使用 Studio。先运行一次 setup-research-os 把项目级 Skills 安装好，再在目标项目的 Claude Code 会话中显式调用如 /research-charter。但 CLI 和 validators 仍是底层组成，不是纯 Markdown Skill 仓库。
为什么 Studio 比 ARIS 麻烦，要写 JSON 和 SHA-256？
它选择了更严格的可追踪性：Agent 必须明确知道本次读取的是哪个文件版本。这增加了前期步骤，但降低“输入被悄悄修改、结果无法复验”的风险。
我是新手，第一天应该做到哪里？
只完成 Studio 教程的前六步：安装、setup、写一个研究问题、创建 request、运行 research-charter、验证并阅读输出。不要第一天就跑完整外循环或实验。
怎么确认终端里的 research-os 是哪个版本？
目前两者包名和版本号相同，单看 --version 不可靠。执行 which research-os 可以看入口位置；最可靠的做法仍是：Studio 使用全局命令，旧版总是通过其仓库执行 uv run --directory "$OLD_REPO" ...。
两个版本能共用同一个科研项目吗？
不建议。请为试用分别创建两个项目目录，例如 my-research-project-studio 和 my-research-project-classic，避免 contracts、安装清单和产物相互污染。
我理想中的纯 Skill 版本应该是什么样？
它会更接近 ARIS：仓库主体是 skills/*/SKILL.md、少量共享 references/templates 和极薄安装器；研究状态由目标项目文件保存，宿主 Agent 执行协议。当前两个 Research OS 都没有完全走这条路线。

现在只做一件事

选择 Studio，创建一个全新的测试科研项目，只跑通 research-charter。完成后，你已经掌握 80% 的日常使用模型：固定输入 → 调用一步 → 验证 → 人工决定。
