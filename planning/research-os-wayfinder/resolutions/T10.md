# 确定数学证明与 Lean 内循环 workflow 边界

## 决策

Research OS 将数学研究拆成彼此独立、由用户显式调用的 workflow。workflow 之间只通过带稳定 ID、来源和 typed relations 的 artifact 衔接；一个 workflow 完成后写出结果、保留失败现场、列出下一步并停止，不自动调用另一个 user-invoked workflow。

P0 采用细粒度边界，而不是一个隐藏“自动证明循环”：

| User-invoked workflow | 输入 → 输出 | 完成与停止点 | 用户可选下一步 |
| --- | --- | --- | --- |
| `conjecture-exploration` | 问题背景、已有文献、定义候选 → `Conjecture`、候选定义与开放问题 | 候选命题和未决假设已记录；不把候选当成事实 | 选择命题、继续找例子，或结束本轮 |
| `example-counterexample` | `Conjecture`/定义 → `Example`、`Counterexample`、覆盖记录 | 达到用户给定的搜索范围或发现反例；找到反例时保留它并停止 | 修订命题，或在无反例时进入形式陈述 |
| `formal-statement` | 选定命题、定义、例外与反例 → 版本化 `FormalStatement` | 对象、量词、假设、结论和语义解释已明确；不暗示可证明 | 建立 lemma map、修订陈述，或结束 |
| `lemma-map` | `FormalStatement` → `Lemma` 与依赖图 | 依赖、缺口和可能的证明顺序已标出；不执行无限拆解 | 选择证明尝试或修订陈述 |
| `proof-attempts` | `FormalStatement`、`LemmaMap`、相关证据 → 多个版本化 `ProofAttempt` | 到达用户指定的尝试数/时间预算、遇到阻塞或形成候选证明；每次失败都保留 | 评审尝试、形式化候选，或修订陈述 |
| `proof-review` | 证明尝试、反例、引理和证据 → `ProofReview`/审计记录 | 检查漏洞、隐含假设、循环论证和与陈述的对应关系后停止 | 修订陈述、重做尝试，或进入 Lean |
| `statement-revision` | 反例或 review → 新版本 `Conjecture`/`FormalStatement` | 变更理由、影响范围和 supersedes 关系已记录；不覆盖旧版本 | 重新找例子、建 lemma map 或尝试证明 |
| `lean-formalization` | 冻结的 `FormalStatement`、`LemmaMap`、选定证明 → Lean source 与候选 `LeanCertificate` | Lean 文件和 toolchain/依赖信息已保存；编译失败也要输出错误与现场 | 修复形式化、重做证明，或请求 kernel verification |
| `kernel-verification` | Lean source、锁定 toolchain/依赖 → 独立 `KernelVerification` | 明确记录 kernel/build 结果、提交、环境、axiom/sorry 使用；失败即停止 | 返回形式化/陈述修订，或将结果用于 claim |
| `paper-alignment` | `FormalStatement`、`KernelVerification`、数学 claim 与论文位置 → `PaperAlignmentAudit` | 逐项核对论文中的表述、假设、证明状态和 Lean 证据；不自动改写论文或升级 claim | 用户决定写作、修订或保留审计结果 |

`proof-attempts` 内可以有有限的多个尝试，`proof-review` 内可以有有限的检查项；有限指令预算由用户在本次调用中给定。它们不是跨 workflow 的隐式 loop，也不能自行选择下一阶段。

## Artifact 与关系

至少保留以下 artifact：`Conjecture`、`Example`、`Counterexample`、`FormalStatement`、`Lemma`/`LemmaMap`、`ProofAttempt`、`ProofReview`、Lean source、`LeanCertificate`、`KernelVerification` 和 `PaperAlignmentAudit`。每个 artifact 都有稳定 ID、版本、provenance、创建时间和状态；修订产生新 ID，并用 `supersedes` 连接旧版本。

建议的 typed relations 包括：

- `Example instantiates Conjecture`；`Counterexample refutes Conjecture`；
- `FormalStatement formalizes Conjecture`；`Lemma supports FormalStatement`；`LemmaMap depends-on Lemma`；
- `ProofAttempt attempts FormalStatement`；`ProofReview reviews ProofAttempt`；`FormalStatement supersedes FormalStatement`；
- `LeanSource formalizes FormalStatement`；`LeanCertificate supports ProofAttempt`；`KernelVerification verifies LeanSource`；
- `PaperAlignmentAudit aligns-with FormalStatement/KernelVerification`。

关系表达的是可追溯连接，不构成中央图调度器或项目全局 phase 状态机。artifact 的失败、阻塞、反例、工具版本和人类决定不得删除或用新结果静默覆盖。

## 硬边界与 assurance

- 模型只能在当前 workflow 内执行局部工作：生成候选、枚举例子、检查定义、整理引理、提出证明尝试、做 review 清单、运行 Lean 或整理对齐报告。模型不能改变研究问题、偷偷放宽陈述、推进下一 workflow、宣布定理成立，或把探索结果直接升级成 publication claim。
- 反例是反驳证据，不是需要被自动绕开的失败；任何 statement revision 都必须由用户显式选择，并产生新版本。
- 数学 review、模型一致意见、Lean 源码可编译和外部专家意见都是不同 assurance 轴，不能互相冒充 kernel 证明。
- 只有记录了明确 kernel/build 结果、固定 toolchain 与依赖、源码 provenance，并列出 axiom 与 `sorry` 使用情况的 `KernelVerification`，才可作为“已形式化验证”的证据。含未披露 `sorry`、失败 build 或缺失环境信息的结果不能支持形式证明 claim。使用公理并非自动禁止，但必须显式列出并在论文/claim 中保持一致。
- `paper-alignment` 只审计“论文说了什么”与“当前 artifact 支持什么”的一致性；发现陈旧或不一致时标记为 stale/gap，不能自动把探索性数学结果升级为正式 claim。

## 明确不做

P0 不提供数学中央 planner、自动反复改题的 agent、无界 proof search、默认自动重试、全局 `current_phase`，也不把 Lean 之外的模型判断包装成 kernel assurance。后续若引入领域 adapter，必须遵守同样的 user-invoked 边界和 artifact contract。
